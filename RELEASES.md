# Releases

Release automation follows [Orhun's automated Rust releases guide](https://blog.orhun.dev/automated-rust-releases/) (2023), updated for current tooling.

## Stack

| Tool | Role | Notes vs the 2023 guide |
| --- | --- | --- |
| [git-cliff](https://git-cliff.org/) | Changelog from conventional commits (`cliff.toml`) | Still release-plz's changelog engine |
| [release-plz](https://release-plz.dev/) | Release PR (version bump + `CHANGELOG.md`), crates.io publish, `vX.Y.Z` tag | Action is now `release-plz/action@v0.5` (was `MarcoIeni/release-plz-action`) |
| [dist](https://axodotdev.github.io/cargo-dist/) (formerly cargo-dist) 0.34 | Binaries, shell/PowerShell installers, checksums, GitHub Release | Config lives in `dist-workspace.toml` |
| Dependabot | Weekly Cargo + Actions PRs, `chore(deps)` commits | Minor/patch Cargo bumps and all Actions bumps are grouped |
| Mergify | — | Skipped: merge Dependabot PRs yourself |

## Workflows

| File | Runs on | Does |
| --- | --- | --- |
| `.github/workflows/ci.yml` | pushes to `main` and `cursor/**`, all PRs | fmt (Linux), clippy and tests on Linux, macOS and Windows, all `--locked`; line coverage ≥ 85% (Linux, cargo-llvm-cov) |
| `.github/workflows/release-plz.yml` | pushes to `main` (repo owner `aldreth` only) | opens/updates the Release PR; publishes + tags versions not yet on crates.io |
| `.github/workflows/release.yml` | `vX.Y.Z` tags; `dist plan` on PRs | builds the five targets and creates the GitHub Release (generated by dist) |

`git_release_enable = false` in `release-plz.toml`, so dist owns the GitHub Release page. Release notes come from the matching `CHANGELOG.md` section.

## Commit messages

The changelog is built from [conventional commits](https://www.conventionalcommits.org/): `feat:`, `fix:`, `perf:`, `refactor:`, `docs:`, `test:`, `style:`, `chore:`/`ci:`. Other messages are left out of the changelog. Below 1.0, breaking changes (`feat!:` or a `BREAKING CHANGE:` footer) bump the minor version and everything else bumps the patch; from 1.0, `feat:` bumps the minor.

History before 0.1.0 is not conventional, so the 0.1.0 changelog entry is hand-written.

## One-time GitHub setup

1. **Settings → Actions → General → Workflow permissions:** allow GitHub Actions to create and approve pull requests.
2. **Secret `RELEASE_PLZ_TOKEN`:** a fine-grained PAT for this repo with **Contents** and **Pull requests** read/write. The tag must be pushed with this token, because tags pushed with the default `GITHUB_TOKEN` don't start other workflows, so `release.yml` would never run.
3. **Secret `CARGO_REGISTRY_TOKEN`:** a crates.io token with `publish-new` and `publish-update`. Alternatively use crates.io [trusted publishing](https://crates.io/docs/trusted-publishing) after the first publish (the workflow already has `id-token: write`).

Set the secrets **before** pushing `main` to GitHub. `publish = true`, so without a registry token the release-plz job fails on every push to `main`. If you want GitHub releases without crates.io, set `publish = false` in `release-plz.toml`.

## Flow

**First release (0.1.0).** The crate isn't on crates.io yet (the name was free when checked on 2026-11-03), so there is no Release PR. On the first push to `main` with the secrets in place, release-plz publishes 0.1.0 and pushes `v0.1.0`. dist then builds the binaries and creates the GitHub Release with the hand-written notes.

**Every release after that:**

1. Land conventional commits on `main`.
2. release-plz opens or updates a **Release PR** that bumps the version, refreshes `Cargo.lock` (`dependencies_update = true`) and adds the new `CHANGELOG.md` section.
3. Edit the changelog in that PR if you like, then merge it.
4. release-plz publishes to crates.io and pushes `vX.Y.Z`.
5. `release.yml` builds archives and installers for macOS (arm64, x86_64), Linux (arm64, x86_64) and Windows (x86_64) and attaches them to the GitHub Release.

## Maintenance notes

- **Rust toolchain:** change the version only in `rust-toolchain.toml`. CI and release-plz install whatever it names, and dist's builds use it too.
- **Minimum supported Rust (`rust-version` in `Cargo.toml`, currently 1.89):** this is what `cargo install` users need, not the pinned toolchain. When a dependency raises it, bump `rust-version` too. Check it with `cargo +1.89 check --locked`.
- **dist and Dependabot:** `release.yml` is generated by dist, but Dependabot bumps the actions in it. `allow-dirty = ["ci"]` in `dist-workspace.toml` stops `dist plan` rejecting those edits (without it, every PR and release fails). Running `dist init` or `dist generate` again rewrites `release.yml` with dist's own action versions; that's fine, and Dependabot will bump them again.

## Local checks

```bash
# What dist would build and the release notes it would use
dist plan
dist plan --tag=v0.1.0 --output-format=json | jq -r .announcement_github_body

# Unreleased changelog entries from conventional commits
git cliff --unreleased

# What release-plz would bump (run in a throwaway clone; it edits files)
git clone . /tmp/rct-release-check && (cd /tmp/rct-release-check && release-plz update)

# Package contents and a full publish rehearsal (no upload)
cargo package --list
cargo publish --dry-run
```

## Profiles

See the README's Development section. In short:

- `dev`: fast rebuilds (`debug = 0`)
- `release`: fast runtime (`lto`, `codegen-units = 1`, `panic = "abort"`)
- `dist`: CI packaging (`inherits = "release"`, `lto = "thin"`)

Re-applying the cargo-wizard templates (`cargo wizard apply fast-runtime release --nightly=off`, and so on) adds `target-cpu=native` to `.cargo/config.toml`; remove it before committing, because it isn't portable.
